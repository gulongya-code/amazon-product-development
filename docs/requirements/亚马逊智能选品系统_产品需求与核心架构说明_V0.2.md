## 1. 文档结论

本系统不是传统的“抓取销量、价格、评论后生成单一分数”的选品工具，而是一个以：

**产品理解 → 需求理解 → 产品-需求匹配 → 真实市场重建 → 机会与风险判断**

为核心主线的智能选品系统。

核心业务逻辑：

> 系统先理解“市场上的商品到底是什么”和“买家真正想要什么”，再识别哪些商品属于真实竞争供给，重建更接近真实需求与真实竞争的市场结构，最后才使用销量、搜索量、价格、评论、CPC、利润、趋势等传统指标做机会判断。

系统负责：

- 数据采集与证据留存；
- 产品事实提取与产品画像构建；
- 搜索需求理解；
- 产品与需求相关性分析；
- 市场结构重建；
- 机会、风险与不确定性解释；
- 为人工选品提供可追溯建议。

系统**不以单一评分替代人的判断**，最终选品决策由人工完成。

## 2. 项目边界

### 2.1 与 Amazon Ads Optimizer 的边界

本选品系统与 Amazon Ads Optimizer **完全独立**：

- 不合并为同一系统；
- 不把选品系统设计为广告优化系统的子模块；
- 不共享运行时、业务状态、数据库或发布节奏；
- 不将未来合并作为当前架构假设；
- 不因为代码复用形成强耦合。

允许借鉴或重写广告优化系统中已经验证过的思想，例如：

- Evidence First；
- Provenance；
- Fail Closed；
- 搜索词相关性证据模型；
- 文本相似度的辅助用途；
- 需求类型与相关性层级思想；
- 人工最终决策边界。

若未来确有稳定通用能力，可另行评估是否抽取公共库，但这不是当前目标。

### 2.2 与每日数据 / 运营今日决策系统的边界

本选品系统与 `daily_data_auto_entry` 等每日数据项目同样保持项目级独立：

- 不共享业务代码；
- 不共享数据库；
- 不共享 Git 历史；
- 不把本系统设计为其扩展模块。

## 3. 系统最终要回答的问题

系统最终应能够帮助回答：

1. 这个市场真正对应什么消费者需求？
2. Amazon 搜索结果中的每个商品分别是什么？
3. 哪些商品是真实核心竞品？
4. 哪些只是部分相关、不同场景、配件、替代品、规格冲突或噪音？
5. 多个关键词是否属于同一个真实 Demand Cluster？
6. 真实需求规模、真实竞争强度和进入门槛是多少？
7. 市场的主要价格带、品牌结构、评论门槛和新品进入情况如何？
8. 消费者有哪些明确痛点与未满足需求？
9. 如果进入，最值得进一步研究的产品方向是什么？
10. 主要风险、不确定性与证据缺口是什么？
11. 哪些结论证据充分，哪些必须由人工继续核验？

## 4. 系统四个核心智能层

### 4.1 Product Intelligence

回答：

> 这个商品到底是什么？

系统面对陌生 ASIN 时，不能要求用户手工提供知识包，而应根据真实商品证据自动生成动态 Product Profile / Product Knowledge Snapshot。

### 4.2 Demand Intelligence

回答：

> 买家到底想买什么？

关键词只是需求入口，不等于完整需求。

### 4.3 Market Intelligence

回答：

> 真实市场结构是什么？

Amazon 搜索结果不等于真实竞品集合，Keyword 也不等于 Demand。

### 4.4 Opportunity Intelligence

回答：

> 这个市场值不值得进入，应该重点研究什么方向？

机会判断必须建立在真实需求与真实供给重建之后。

## 6. Provider-Agnostic Architecture

系统核心不得绑定单一数据供应商。

数据供应商应通过可替换 Provider Adapter 接入：

```text
Provider
   ↓
Provider Adapter
   ↓
Canonical Data / Evidence
```

Canonical Model 中不得出现业务核心字段：

- `xiyou_sales`
- `xiyou_keyword_rank`
- `sorftime_brand`
- `sorftime_attributes`

Provider 信息必须作为 provenance / metadata 存在，而不是成为业务模型本身。

### 6.1 Single-Provider Mode

系统必须支持 Single-Provider Mode。

这意味着：

- 只有 XiYou 时，可以运行 XiYou 能支撑的分析；
- 只有 Sorftime 时，可以运行 Sorftime 能支撑的分析；
- 不得要求 `provider_count >= 2` 才能生成 Canonical Observation；
- 多 Provider 是增强能力，不是系统运行前置条件。

“系统支持单 Provider”不等于“当前某一个 Provider 已经能够覆盖全部业务需求”。

## 8. 数据证据四层级

系统正式区分：

### 8.1 OBSERVED

Provider 报告的直接可观察事实，例如：

- title；
- price；
- rating；
- review_count；
- rank；
- listing attribute。

### 8.2 PROVIDER_ESTIMATE

Provider 估算或计算指标，例如可能包括：

- sales；
- orders；
- traffic；
- search volume；
- revenue。

具体分类必须依据 Provider 的真实语义，不能凭字段名称猜测。

### 8.3 RESOLVED

系统基于一个或多个 Observation，在明确 policy 下得到的稳定输入事实。

Resolved 不得丢失原始证据、冲突与 provenance。

### 8.4 DERIVED

后续 AI / Rules / Analytics 推导结果，例如：

- Product Profile；
- Demand Profile；
- Relevance；
- True Competitor；
- Demand Cluster；
- Opportunity Judgment / Score。

流程：

```text
OBSERVED + PROVIDER_ESTIMATE
              ↓
          RESOLVED
              ↓
           DERIVED
```

## 9. Evidence First 与 Provenance

任何重要 Observation 都必须尽可能保留：

- provider；
- source_tool；
- source_field；
- source_record_identity；
- observed_at；
- retrieved_at；
- period；
- scope；
- unit；
- provider_method（如可得）；
- raw_evidence_reference。

系统必须能够从后续 Resolved / Derived 结果回溯到原始 Provider Evidence。

原始 Provider Evidence 原则：

- 尽量 immutable；
- 不静默修改；
- 不因为标准化而删除未知字段；
- 本地保留与 Git 是否跟踪属于独立的工程策略。

### 9.1 Transformation Provenance

从 Raw Provider Evidence 生成 Canonical Observation 时，lineage 不能只指向 raw evidence，还必须能够识别产生该结果的采集与转换上下文。

至少应在适用时记录：

- `collection_run_id`；
- `provider_schema_version`（Provider 可提供时）；
- `mapping_version`；
- `transformation_run_id` 或等价的转换代码版本引用。

同一份 raw evidence 经不同 mapping / transformation 版本产生的结果必须能够区分和复现。来源未提供的版本信息应显式保留为未知，不得猜测填充。

## 10. Unknown / Missing / Zero 是不同状态

系统必须将以下状态视为一等公民：

- `UNKNOWN`
- `MISSING`
- `SEMANTICS_UNCONFIRMED`
- `QUERY_RETURNED_EMPTY`
- 数值 `0`

它们不能互相替代。

例如：

```text
Keyword → ASIN = empty
```

只表示该次查询没有返回候选结果。

它**不等于**：

```text
market_size = 0
competitor_count = 0
demand = 0
```

同样：

Review helpful votes 未提供，不得默认成 `0`。

## 12. 数据冲突与 Resolution 原则

当前至少需要支持以下语义：

- `CONSISTENT`
- `MINOR_DIFFERENCE`
- `MATERIAL_DIFFERENCE`
- `SEMANTIC_CONFLICT`
- `UNIT_CONFLICT`
- `DIRECTIONAL_CONFLICT`
- `ONE_SOURCE_ONLY`
- `NOT_DIRECTLY_COMPARABLE`
- `UNKNOWN`

### 12.1 不允许简单平均

例如：

```text
XiYou rating = 4.6
Sorftime rating = 4.1
```

不能直接：

```text
resolved_rating = 4.35
```

应先保留为：

`MATERIAL_DIFFERENCE`

再由后续 policy 根据 freshness、scope、provider semantics 等决定是否可以解析。

### 12.2 字段级问题不应无条件阻断整商品

例如：

```text
review_count = 75 vs 78
```

可以标记 `MINOR_DIFFERENCE`，但不应因此使整个 Product Intelligence BLOCKED。

系统必须支持 field-level issue / resolution。

### 12.3 单 Provider 证据是合法证据

只有一个 Provider 提供某字段：

`ONE_SOURCE_ONLY`

不等于：

`INVALID`

## 13. Unit 与 Semantic Safety

数值与单位必须绑定。

错误设计：

```text
pressure = 1000
```

正确方向：

```text
dimension = pressure_rating
numeric_value = 1000
unit = ...
raw_value = ...
source = ...
normalization_status = ...
```

真实验收案例：

```text
1000 pascal
1000 WOG
1000 PSI
```

必须：

- 保留全部原始证据；
- 不因为 numeric value 相同而合并；
- 标记 `UNIT_CONFLICT` / semantic issue；
- 在没有安全规则时保持 `UNRESOLVED`。

正式单位注册表、WOG 语义和安全换算规则属于后续策略任务。

## 15. Product Intelligence 需求

### 15.1 基本原则

系统不能要求用户为陌生 ASIN 手工创建产品知识包。

流程：

```text
Raw Product Evidence
        ↓
Canonical Product Evidence
        ↓
Resolved Product Evidence
        ↓
Product Knowledge Snapshot
```

Product Profile 是动态生成的快照，而不是人工维护的静态数据库。

### 15.2 Product Intelligence 证据来源

可包含：

- Title；
- Brand；
- Category；
- Structured Attributes；
- Description；
- Bullet Points（如来源提供）；
- Technical Details；
- Variations；
- Images / Image Text（后续增强）；
- Reviews；
- A+（后续增强）；
- 其他合规产品证据。

### 15.3 产品理解维度

第一版至少应能够表达并提取：

- product_type；
- core_function；
- material；
- size；
- interface；
- structure；
- color；
- style；
- quantity；
- compatibility；
- use_case；
- audience；
- problem_solved；
- brand；
- model；
- certification（如有）；
- product_role。

### 15.4 证据状态

不得只输出最终值。

至少需要表达：

- explicit / confirmed；
- inferred；
- uncertain；
- conflicting；
- missing。

### 15.5 Title-only 不得伪装为完整画像

如果某产品只有 Title：

Product Intelligence 最多判为：

`PARTIAL`

不能因为 AI 可以猜测而输出 READY。

## 16. Demand Intelligence 需求

Keyword 不等于 Demand。

系统应将 Keyword 转换为 Demand Profile，至少考虑：

- demand_object；
- function；
- attributes；
- specification；
- compatibility；
- use_case；
- audience；
- problem_solution；
- brand_or_model；
- search_intent；
- ambiguity；
- missing evidence。

例如：

`quiet mini fridge for bedroom`

不能只当成字符串，而应理解为：

- Object = mini fridge
- Attribute = quiet
- Use Case = bedroom
- Underlying Need = low-noise / sleep-friendly

Demand Intelligence 应消费：

> Canonical Keyword Evidence

而不是直接依赖 XiYou JSON。

---

## 17. Demand Cluster

多个关键词可能是同一真实需求的不同表达。

例如未来系统需要识别：

```text
keyword A
keyword B
keyword C
      ↓
同一 Demand Cluster
```

因此不能简单把多个相关关键词的搜索量直接求和。

Demand Cluster 应在需求语义与统计口径明确后形成。

---

## 18. Product–Demand Relevance

核心逻辑：

```text
Product Profile × Demand Profile
              ↓
       Relevance Result
```

判断至少应考虑：

- 搜索对象是否一致；
- 核心功能是否满足；
- 关键属性是否匹配；
- 规格是否兼容；
- 使用场景是否匹配；
- 目标用户/对象是否匹配；
- 是否属于配件；
- 是否属于替代产品；
- 是否存在明确冲突；
- 是否存在足够证据。

### 18.1 文本相似度边界

以下方法均不能单独作为最终相关性判断：

- 标题包含关键词；
- RapidFuzz；
- 编辑距离；
- token similarity；
- 单一 embedding similarity；
- Amazon 搜索结果中出现该 ASIN。

文本相似度可以用于：

- 关键词去重；
- 候选预筛；
- 近似词发现；
- 聚类预处理；
- duplicate detection。

但其输出仅作为辅助 evidence。

## 19. Market Reconstruction

### 19.1 Search Result ≠ Competitor

Amazon 搜索结果中的 ASIN 只是候选供给观察。

系统需要进一步分类：

- Core Competitor；
- Relevant；
- Partial / Scenario Adjacent；
- Accessory；
- Alternative Product；
- Specification Conflict；
- Unrelated；
- Unknown / Review Required。

最终形成：

`True Competitor Set`

### 19.2 Directional Evidence

Market Reconstruction 不能简单写成：

```text
candidate_asins = get_keyword_asin_analysis(...)
```

至少应允许综合：

```text
Forward Evidence
Keyword → ASIN

+

Reverse Evidence
ASIN → Keyword

+

Other Ranking / Traffic Evidence
```

然后再进行 Resolution。

### 19.3 正向为空不得推导市场为空

TASK-SP-001 已经证明 Provider 内部可能存在方向不一致。

因此：

`QUERY_RETURNED_EMPTY`

只是证据状态，不是市场事实。

### 19.4 Parent / Child Aggregation Safety

Market Reconstruction 不得默认将 Parent ASIN 与其每个 Child ASIN 都视为相互独立的竞品或销量单元。

在计算 competitor count、sales、revenue 或 market size 前，必须：

- 明确候选集合采用 Parent、Child 还是混合粒度；
- 保留 parent / child 关系的来源、时间与完整性状态；
- 使用显式、版本化的去重与聚合 policy，避免父子体重复计数；
- 将由父体指标向子体分配得到的数值标记为 `DERIVED`，并保留方法、版本、假设与输入引用；
- 在关系不完整或聚合口径无法确认时保留 `SCOPE_UNCONFIRMED` / `UNRESOLVED`，不得猜测补齐。

## 21. Demand–Supply Gap

未来可结合：

- Demand Profile；
- Search / Keyword；
- Product Attributes；
- Reviews；
- Product Fact；
- True Competitor Set；

寻找：

> 消费者明确需要，但当前主流供给没有很好满足的需求。

例如：

高需求包含 `quiet`，而主流真实竞品 Review 大量反馈噪音问题，则可能形成：

`Demand–Supply Gap`

但必须保留证据与不确定性，不能因为单条评论直接下结论。

- 主要产品形态；
- 消费者痛点；
- 未满足需求；
- 推荐进一步研究方向；
- 主要风险；
- Provider 数据冲突；
- 哪些结论证据充分；
- 哪些结论需要人工复核。

Opportunity Score 可以存在，但只是解释层补充，不代替最终结论。

## 33. 系统核心设计原则

1. **Evidence First**：重要结论尽可能有原始证据。
2. **Provider Agnostic**：核心模型不依赖 XiYou、Sorftime 或其他单一供应商。
3. **Single-Provider Capable**：只有一个 Provider 也能运行可支持的能力。
4. **Fail Closed**：关键证据冲突或语义不明时允许 UNRESOLVED。
5. **Do Not Over-block**：局部小差异不能无条件阻断整个商品。
6. **Missing ≠ Zero**：缺失、空结果、未知与 0 必须区分。
7. **Observation ≠ Truth**：Provider Observation 不是最终系统事实。
8. **Estimate ≠ Observed Fact**：Provider Estimate 必须显式标记。
9. **Similarity ≠ Relevance**：文本相似度只作为辅助证据。
10. **Keyword ≠ Demand**：关键词需要进一步构建 Demand Profile / Cluster。
11. **Search Result ≠ Competitor**：搜索结果必须经过真实相关性重建。
12. **Direction Matters**：Keyword → ASIN 与 ASIN → Keyword 不得合并丢失方向。
13. **Unit Matters**：相同数字不同单位不得视为同一事实。
14. **Provenance Required**：Resolved / Derived 结果必须尽量可追溯。
15. **No False Precision**：数据供应商分歧、估算和不确定性不能被虚假精确值掩盖。
16. **Human Final Decision**：系统提供分析和建议，最终选品由人决定。
17. **Project Independence**：与广告优化、每日数据项目保持独立。
18. **MVP First**：先验证核心认知闭环，再扩展复杂机会评分。

## 34. V0.2 验收标准

本需求基线应满足：

- 明确系统不是传统指标打分工具；
- 明确 Product Intelligence 必须自动理解陌生 ASIN；
- 明确 Demand Intelligence 必须把 Keyword 转化为 Demand；
- 明确 Product × Demand Relevance 是 True Competitor 的核心基础；
- 明确文本相似度不能单独决定相关性；
- 明确 Search Result 不等于 Competitor；
- 明确 XiYou / Sorftime 只是当前 Provider 角色，不得硬编码；
- 明确支持 Single-Provider Mode；
- 明确 OBSERVED / PROVIDER_ESTIMATE / RESOLVED / DERIVED；
- 明确 Missing / Unknown / Empty / Zero 的区别；
- 明确 Provider disagreement 不能简单平均；
- 明确单位与 semantic conflict 必须 fail closed；
- 明确正向 / 反向 Keyword-ASIN 证据保留方向；
- 明确 Canonical Evidence 是下游智能层唯一合法的数据入口方向；
- 明确 XiYou + Sorftime 当前足够支撑核心 MVP，但存在限制；
- 明确第一阶段不自动做最终选品决策；
- 明确与 Amazon Ads Optimizer、每日数据系统完全独立；
- 能作为后续 Codex 正式开发任务的上位需求依据。
