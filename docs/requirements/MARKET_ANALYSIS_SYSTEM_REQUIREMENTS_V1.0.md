SellerSprite 导入 + Sorftime 深挖 + 11-Sheet 运营模板

版本 V1.0 · 2026-08-26

目标：把现有选品 Excel 模板升级为可重复运行、可跨类目、可审计的市场分析与产品方向决策系统。

# 文档摘要

> 本版本以用户提供的实际市场分析工作簿为运营输出标准：11 个可见 Sheet、4 个隐藏后台 Sheet。系统不再以“全部数据必须 API 自动抓取”为目标，而采用“卖家精灵批量导入负责市场广度、Sorftime 按需负责深度、代码负责结构化计算、AI 负责语义理解与解释”的混合架构。

| **决策项**     | **V1.0 决策**                                                                                     |
|----------------|---------------------------------------------------------------------------------------------------|
| 大样本市场数据 | 优先手动导入 SellerSprite XLSX/CSV；目标 500–1500 Listings。                                      |
| Sorftime       | 不重复抓取全市场；只用于代表性 ASIN、关键词、Review/Customer Say 等深度补充。                     |
| 运营输出       | 复用现有 11 个可见 Sheet 的业务结构与主要公式。                                                   |
| 后台结构       | 保留/升级 4 个隐藏 Sheet：自动化配置、原始数据源、关键词数据源、自动化辅助。                      |

# 1. 产品定位与目标

系统定位：亚马逊类目级市场研究与产品开发方向决策系统。它不是单纯的数据抓取器，也不是让 AI 自由推荐产品，而是把第三方市场数据、结构化规则、可复核公式、关键词/评论证据和人工供应链判断串成一个可重复的决策流程。

核心目标：

- 上传一份 SellerSprite 市场导出表后，系统可自动完成字段识别、数据清洗、类目结构拆解、市场统计和模板填充。
- 跨类目使用时，只替换/生成当前类目的语义规则，不修改通用统计逻辑。
- 在“还不知道要开发什么产品”的前提下，先发现市场中真实存在的产品路线，再评估哪些路线值得进一步研究。
- 只有在候选路线形成后，才选择代表性 ASIN 使用 Sorftime 深挖；真正的直接竞品必须等产品方向锁定后再定义。
- 用统一、可配置的 30% 目标毛利模型倒推出厂采购价上限，交给运营/采购判断是否可实现。
- 最终给同事的 Excel 保持接近现有模板的运营语言与使用习惯，而不是暴露底层技术模型。

MVP 非目标：

- 不要求用 Sorftime 自动获取 500–1000 个全市场商品。
- 不在 MVP 中处理 LQS、CPF 绿标、SP 广告。
- 不自动给出专利/商标“安全”结论；侵权只允许输出待核查清单。
- 不把 SellerSprite/Sorftime 的估算值表述为 Amazon 官方真实销量。
- 不在产品方向尚未确定时提前生成“直接竞品集”。

# 2. 用户与核心工作流

1. **步骤 A｜上传市场数据**：SellerSprite 导出 500–1500 个 Listing，系统识别字段和数据日期。
2. **步骤 B｜建立 Product Map**：解析“详细参数 + SKU + Title”，形成材质、安装方式、结构容量、Pack、场景、特殊功能等标准属性。
3. **步骤 C｜发现产品路线**：基于属性相似度与类目规则形成多个 Product Archetype，并计算每条路线的销量、Listing、增长、价格、Review、新品等指标。
4. **步骤 D｜候选路线**：从路线级机会指标中选择 3–5 条彼此有差异的候选路线；输出为什么值得继续研究。
5. **步骤 E｜代表性 ASIN 深挖**：每条候选路线选择 3–5 个代表性 ASIN，按预算调用 Sorftime 获取关键词/Review/Customer Say 等深度证据。
6. **步骤 F｜产品方向比较**：AI 在受约束数据上解释用户需求、痛点与结构性机会，形成候选开发方向。
7. **步骤 G｜成本可行性**：按 30% 目标毛利率倒推出厂采购价上限，人工判断供应链是否可达。
8. **步骤 H｜方向锁定后**：再定义 10–30 个 Direct Competitors，做更深的竞品与样品规格研究。

# 3. 数据输入与数据源策略

| **数据层**      | **主数据源**          | **用途**                                                                           | **原则**                                 |
|-----------------|-----------------------|------------------------------------------------------------------------------------|------------------------------------------|
| 市场广度        | SellerSprite 手动导出 | 类目规模、销量/销售额、价格、Review、BSR、卖家、上架时间、FBA、详细参数等。        | 优先复用；避免重复 API 成本。            |
| 商品/关键词深度 | Sorftime              | 代表性 ASIN 关键词、排名、搜索量、CPC、流量份额；按需补 Review/Customer Say/变体。 | 预算可控；不做全量 1000 ASIN 重复抓取。  |
| 供应链          | 人工输入              | 预估采购成本、是否可实现、MOQ/工艺风险等。                                         | 人工事实，不由 AI 猜测。                 |
| 分析计算        | 系统代码              | 聚合、分布、集中度、增长、机会指标、成本上限。                                     | 确定性优先。                             |
| 解释层          | AI                    | 类目专属路线命名、歧义属性解释、痛点总结、方向对比、综合说明。                     | 只能引用已有证据，不得生成不存在的数字。 |

导入文件必须记录：source_type、文件名、文件 SHA-256、导入时间、数据观察日期（如可用）、市场站点、类目、原始行数、有效 ASIN 数、被剔除/待复核行数。

# 4. 模板合同与输出结构

当前目标模板实际包含 15 个 Sheet，其中 11 个可见、4 个隐藏。系统必须把“可见运营页”和“隐藏计算/数据页”分开管理。

| **类型** | **Sheet**         | **系统职责**                                          |
|----------|-------------------|-------------------------------------------------------|
| 可见     | 综合说明          | AI + 代码结果生成运营摘要；不得手填旧样例。           |
| 可见     | 类目              | 当前市场/类目基础信息。                               |
| 可见     | 市场调研          | 市场规模、集中度、趋势、新品、内容等。                |
| 可见     | 竞品数据          | 导入数据 + 标准化属性 + 派生字段。                    |
| 可见     | 不同维度分析      | 主要复用现有公式；参数化价格/Review/FBA/时间等分档。  |
| 可见     | 分析模型对比      | 复用/校准现有公式，用于多个模型/路线对比。            |
| 可见     | top100—日单量分析 | 从导入数据排序筛 Top100，不额外调用 API。             |
| 可见     | 产品初步筛选范围  | 系统生成候选路线及证据。                              |
| 可见     | 价格核算          | 重建为可审计的 30% 目标毛利倒推采购成本模型。         |
| 可见     | 样品类型          | 候选产品方向/规格假设；语义为待验证，不是最终立项。   |
| 可见     | 竞品收集          | 方向锁定后生成直接竞品；方向锁定前仅允许代表性 ASIN。 |
| 隐藏     | 自动化配置        | 字段映射、通用分档、当前类目语义规则、成本参数。      |
| 隐藏     | 原始数据源        | SellerSprite 导入区；字段名驱动，不依赖固定列序。     |
| 隐藏     | 关键词1—数据源    | Sorftime/其他关键词证据标准化区。                     |
| 隐藏     | 自动化辅助        | 大规模公式/辅助字段；保持可审计、可重算。             |

> 模板当前公式规模约 26,738 个，其中“自动化辅助”约 24,514 个、“不同维度分析”约 1,150 个、“关键词1—数据源”约 961 个、“分析模型对比”约 108 个。MVP 应优先复用已经正确的公式，而不是重新实现全部 Excel 逻辑。

重要边界：Excel 公式是运营交付与审计镜像，不是系统唯一计算引擎。AI 和 JSON 输出依赖的关键指标必须在代码层可重复计算，避免依赖用户打开 Excel 后才重算。

# 6. Listing 属性提取与 Product Map

系统必须优先用代码解析“详细参数”。当前模板示例已经是 `Key:Value | Key:Value` 结构，可直接拆成属性字典；Title/SKU 仅作为补充和歧义消解。

| **优先级** | **证据**       | **用途**                                                                                 |
|------------|----------------|------------------------------------------------------------------------------------------|
| 1          | 结构化详细参数 | Brand、Material、Mounting Type、Dimensions、Special Feature、Number of Compartments 等。 |
| 2          | 独立导出字段   | 价格、销量、Review、FBA、上架时间等。                                                    |
| 3          | SKU/变体描述   | Pack、颜色、尺寸等补充。                                                                 |
| 4          | Title          | 补充产品形态、Pack、结构卖点、场景；必须标记推断。                                       |
| 5          | AI             | 只处理规则无法确定的歧义或给 cluster 命名；不能覆盖明确结构化事实。                      |

跨类目通用属性维度至少包括：product_form、mounting_or_usage_mode、material_family、size_or_capacity、pack_count、use_case、compatibility、operation_mode、power_mode（如适用）、special_features。

每个提取字段必须带 evidence_status：OBSERVED_STRUCTURED / OBSERVED_LISTING / INFERRED_RULE / INFERRED_AI / UNAVAILABLE，并保留来源文本片段或 source field。

类目规则不得写死在代码中。当前模板“自动化配置”已经证明可行：通用维度不依赖类目规则，产品类型/材质/结构容量/安装方式只读取“当前类目规则”。系统应把这一思想升级为 versioned CategoryRulePack。

# 7. 市场结构、增长与机会指标

第一层目标不是“推荐产品”，而是建立市场地图并评价每条产品路线。

| **指标**            | **定义/计算原则**                                                                   | **解释**                                                         |
|---------------------|-------------------------------------------------------------------------------------|------------------------------------------------------------------|
| Route Sales Share   | 路线月销量 / 全市场有效月销量                                                       | 需求规模。                                                       |
| Route Listing Share | 路线有效 Listing 数 / 全市场有效 Listing 数                                         | 供给数量。                                                       |
| Demand Efficiency   | Route Sales Share / Route Listing Share                                             | >1 表示相对少的供给取得更高销量；仅作结构效率，不等于利润机会。 |
| 聚合环比/同比       | 用每个 ASIN 当前销量与有效增长率还原上期销量后再聚合；无效 -100%/缺失数据不得硬算。 | 路线层增长。                                                     |
| 新品销量占比        | 指定新品窗口内产品销量 / 路线销量                                                   | 新品进入能力。窗口可配置。                                       |
| 新品效率            | 新品销量占比 / 新品Listing占比                                                      | 新品是否获得超额销量。                                           |
| Review Barrier      | 销量加权/分位数 Review、低 Review 商品销量占比                                      | 评价门槛。                                                       |
| Price Opportunity   | 路线价格中位数、销量加权价、价格带销量效率                                          | 经济空间。                                                       |
| Concentration       | 品牌/商品/卖家 TopN 销量占比                                                        | 头部垄断程度。                                                   |
| Content Adoption    | A+/视频等占比（仅在数据有效时）                                                     | 内容成熟度，不作为因果。                                         |

“差异化空间”必须拆成两类：

- 结构性机会空间：由 SellerSprite 大样本直接计算，例如供给少但销量高、新品效率高、Review门槛相对低、高价带仍有需求等。
- 用户问题型差异化空间：必须等代表性 ASIN 的 Review/Customer Say/关键词证据到位后再判断，例如漏水、安装不牢、尺寸冲突、耐用性等。

# 8. 候选产品路线与代表性 ASIN

Product Archetype（产品路线）不是“用户需求”。例如便携/网袋式、粘贴壁挂式、伸缩杆式属于产品路线；租房不愿打孔、宿舍需要便携、担心锈蚀才属于用户需求。系统必须分开建模。

路线发现机制：

1. 对每个 ASIN 建立规范化属性向量/属性签名。
2. 先按强语义维度形成基础组（产品形态、安装/使用方式、主要结构），再用材质/容量/Pack/场景等做细分。
3. 对过碎分组使用确定性相似度合并；AI只给组命名和解释，不直接决定成员归属。
4. 对每条路线计算第 7 节指标，并输出 evidence coverage。
5. 选择 3–5 条候选路线时加入“多样性约束”，避免前5名其实是同一条路线的近义版本。

代表性 ASIN 不是直接竞品。每条候选路线默认选择 3–5 个代表性 ASIN：头部畅销款、最典型款（medoid/中心款）、低 Review 或较新品但表现较好的进入样本、价格边界/高端款，必要时再加一个结构异常样本。

只有当产品方向被人工或系统流程标记为 DIRECTION_LOCKED 后，才允许生成 Direct Competitor Set。

# 9. Sorftime 深挖策略

Sorftime 的职责是“深度补充”，不是替代 SellerSprite 全量市场快照。

| **阶段**     | **对象**                   | **Sorftime用途**                                                        | **预算原则**                             |
|--------------|----------------------------|-------------------------------------------------------------------------|------------------------------------------|
| 候选路线研究 | 每条路线 3–5 个代表性 ASIN | 关键词关系、自然排名、搜索量、CPC、流量份额；按需 Review/Customer Say。 | 默认 15–25 ASIN，总量可配置。            |
| 方向锁定后   | 10–30 个直接竞品           | 更深的关键词/Review/变体/用户痛点验证。                                 | 二阶段预算，需显式触发。                 |
| 全市场       | 500–1500 Listings          | 默认不调用。                                                            | 除非未来实测 API 成本/覆盖优于手工导入。 |

每次 enrichment run 必须有硬预算：最大 ASIN 数、最大操作数、最大重试数（默认0或受控）、实际 consumed、remaining、失败后是否允许继续。不可因一个接口失败自动切换到另一 Provider。

# 10. 30% 毛利倒推采购成本模型

原模板“价格核算”页当前没有公式，保存的是已经计算好的结果值，因此 V1.0 要把计算规则正式系统化，不能继续依赖旧结果。

> 默认业务定义：目标毛利率 30%，以售价为分母；采购成本上限不含头程、不含广告、不含退货损耗。Amazon referral fee、FBA fee 和可确定的平台费用先扣除，再保留目标毛利。所有参数必须可配置。

核心公式：

`MaxProcurementUSD = SellingPriceUSD × (1 − TargetGrossMargin) − ReferralFeeUSD − FBAFeeUSD − OtherPlatformFeesUSD`

`MaxProcurementCNY = max(0, MaxProcurementUSD × FX_USD_CNY)`

`UnitProcurementCeilingCNY = MaxProcurementCNY ÷ PackCount`

若 MaxProcurementUSD ≤ 0，则输出“目标不可达”，不得输出负采购价。

| **参数**          | **默认/来源**                              | **要求**                        |
|-------------------|--------------------------------------------|---------------------------------|
| TargetGrossMargin | 30%                                        | 可配置；模板/报告显示当前参数。 |
| ReferralFeeRate   | 按类目配置；无证据不得默认硬编码到所有类目 | 优先明确类目费率。              |
| FBAFeeUSD         | SellerSprite 导入或后续 API/人工           | 缺失时成本可行性=PARTIAL。      |
| OtherPlatformFees | 默认0，仅明确费用才填写                    | 不得把广告/头程混入毛利模型。   |
| FX_USD_CNY        | 配置项                                     | 记录使用汇率与日期。            |
| PackCount         | 代码从 SKU/Title/结构字段抽取并人工可修正  | 不得把 Pocket/Tier 当 Pack。    |

系统还应提供“我方预估采购成本（人工输入）”和差额：MarginOfSafety = ProcurementCeiling − EstimatedSupplierCost，并输出“可达 / 偏紧 / 不可达 / 缺数据”。

# 11. AI 分析职责与边界

| **AI 可以做**                                              | **AI 不可以做**                                    |
|------------------------------------------------------------|----------------------------------------------------|
| 对规则生成的产品路线命名、合并近义表达、生成中文运营解释。 | 不能编造销量、价格、Review、费率、搜索量。         |
| 总结代表性 ASIN 的关键词/Review/Customer Say 共性与痛点。  | 不能把少量代表样本表述为完整市场用户需求。         |
| 比较候选路线的优缺点，生成验证清单。                       | 不能在产品方向未锁定时把代表性 ASIN 叫“直接竞品”。 |
| 生成综合说明、产品初步筛选范围、样品类型假设。             | 不能将 Product Direction 表述为确定立项/成功保证。 |
| 指出数据缺口和需要人工确认的供应链/合规项。                | 不能自动判定无侵权或供应链一定可实现。             |

# 12. 系统架构与数据流

SellerSpriteImportAdapter
→ 标准化字段 + 来源/缺失语义
→ MarketDataset / Evidence Layer
→ Listing parser + CategoryRulePack
→ Product Map
→ 路线聚合 + 分布 + 增长 + 集中度
→ Route Opportunity Engine
→ 3–5 候选路线 + Representative ASINs
→ Sorftime Enrichment（可选）
→ Keywords / Review / Customer Say evidence
→ Direction Comparison + Buyer Need
→ 30% 成本模型 + 人工供应链输入
→ Operator Template View
→ 11-Sheet XLSX + JSON/Manifest + Evidence Gaps

架构原则：现有 V0.2 strict Market Report / Evidence / Provenance 能复用的必须复用；新模板属于 operator delivery view，不应反向污染或弱化底层严格合同。

# 14. 验收标准

1. 使用当前 998 Listing 模板数据，仅保留原始输入和配置后，系统可重新生成市场统计、Product Map、候选路线和运营输出。
2. 核心市场总销量/销售额、价格分布、Review分布、卖家/品牌集中度等与原模板现有公式结果在定义一致时达到可解释的数值一致；若公式存在旧硬编码，则以新合同为准并记录差异。
3. 系统能自动解析当前类目的 Material / Mounting Type / Pack / Structure / Color 等，并把置信不足标成 REVIEW_REQUIRED。
4. 至少形成 3 条有证据支持、彼此不同的产品路线；每条路线可查看销量占比、Listing占比、增长、新品、Review、价格和集中度。
5. 每条路线可确定性选择 3–5 个代表性 ASIN；方向未锁定前不得产生 Direct Competitor Set。
6. 30%目标毛利采购成本上限由代码计算；输入缺失时明确 PARTIAL；负值显示“目标不可达”。
7. Sorftime 深挖仅发生在显式选择的代表性/直接竞品 ASIN；运行清单记录调用数与预算。
8. 生成最终 Excel 时 11 个运营 Sheet 可见、4 个后台 Sheet 隐藏；无关键公式错误。
9. 用第二个不同类目完成跨类目验证：通用代码不变，只更换 CategoryRulePack / 类目配置。
10. 所有自动化测试禁止真实外部网络，live Sorftime 只在专门验收任务中受控执行。

# 16. 公共 GitHub 代码复用政策

在任何 SP-041 功能实现前，必须先完成公共 GitHub 复用审计。审计优先级：

1. 现有仓库内部可复用模块。
2. 具有 MIT / Apache-2.0 / BSD 等允许商业复用许可证的公开实现或成熟依赖。
3. 无许可证、All Rights Reserved 或许可证不明确的项目仅允许参考架构/测试思路，不得复制代码。
4. 公开仓库代码即使允许复用，也必须经过本项目合同、数据语义、缺失值、确定性和测试门槛，不允许为“复用”而放宽现有严格合同。
5. 每个 Codex Task 完成报告必须包含 Public GitHub Reuse Audit：搜索范围、候选仓库、许可证、采用/拒绝原因、实际复用文件/依赖、保留的版权/许可证要求。

当前第一轮公开仓库审计见 `docs/engineering/PUBLIC_GITHUB_REUSE_AUDIT_V1.0.md`。
